# Development Log: 2026-06-12

## Goal

Add DeepSeek V4 Flash as an alternative explanation provider and make it the default hosted option, while making the provider preference clear to future agents.

## Work Completed

- Added a DeepSeek explanation provider using the OpenAI-compatible Chat Completions API.
- Set the default explanation provider to `deepseek`.
- Set the default DeepSeek model to `deepseek-v4-flash`.
- Kept `rules_based` as the fallback provider.
- Updated `.env.example`, `README.md`, `AGENTS.md`, and architecture/product documentation.
- Added tests for DeepSeek request construction and missing-key fallback behavior.
- Added ADR 0024 documenting the provider-default decision.

## Problems Encountered

- The existing documentation still described rules-based generation as the default and framed Gemini/OpenAI as the only hosted comparison paths.
- A default hosted provider can fail in local environments without an API key, so fallback behavior remains necessary.

## Solution

DeepSeek is now a first-class explanation provider with `EXPLANATION_PROVIDER=deepseek` as the default. The provider sends the existing evidence-grounded prompt payload to `https://api.deepseek.com/chat/completions` with `deepseek-v4-flash`.

The rules-based provider remains the operational fallback so local development can still generate explanations without a hosted API key.

## Next Steps

- Run side-by-side quality evaluations for DeepSeek, Gemini, OpenAI, and rules-based output on the same anomaly set.
- Verify live DeepSeek responses against stored evidence before treating the new default as analytically mature.
- Continue tightening prompts where model output overstates weak contextual evidence.

## Problems Encountered

## Solution

The report now uses a reporting-specific SQLAlchemy engine with a five-second PostgreSQL connection timeout. If the database is unavailable, the command exits with an explicit message.

The report can now distinguish detector changes that create useful episode evidence from detector changes that merely inflate isolated anomalies.

## Additional Work: Change-Point Volatility Scoring

## Goal

Fix an audit-relevant blind spot in the change-point detector where volatility shifts were classified but not scored correctly.

## Work Completed

- Updated change-point severity scoring to use the larger of mean-shift and volatility-shift evidence.
- Added volatility metadata to persisted change-point anomalies.
- Made volatility-shift direction reflect volatility increase or decrease.
- Added a regression test for a pure volatility-regime change.
- Added a bug record documenting the issue and fix.
- Updated the anomaly engine architecture documentation.

## Problems Encountered

The detector classification and severity rules were inconsistent:

- event type could be `volatility_shift`
- severity still depended only on `delta_mean`

That caused stable-mean volatility changes to look weak.

## Solution

The detector now computes both component scores and persists the larger one as the event severity. Metadata keeps both component scores visible for audit.

## Additional Work: Integration Test Database Timeout

## Goal

Make the full backend test suite usable when local PostgreSQL is unavailable.

## Work Completed

- Added a short PostgreSQL connection timeout to the integration test admin engine.
- Added the same timeout to the integration test database engine.
- Re-ran the full backend suite.

## Problems Encountered

The full backend suite previously timed out when PostgreSQL was unavailable because the integration fixture could wait on database connection attempts for too long.

That created weak verification: non-database tests were passing, but the full suite could not complete.

## Solution

The integration fixture now uses a five-second PostgreSQL connection timeout. If the database is unavailable, integration tests skip cleanly through the existing `pytest.skip` path.
