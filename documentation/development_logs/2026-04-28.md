# Development Log - 2026-04-28

## Goal

Make the event-grounded context refresh workflow practical to run locally after full live provider refreshes stalled on network waits and GDELT rate limiting.

## Work Completed

- Added bounded CLI execution to `scripts/news/fetch_news_context.py`.
- Added `--local-only`, `--provider`, `--limit`, and `--start-after-id` options for news context refreshes.
- Changed news context refresh execution to process anomalies one at a time with progress output and independent transactions.
- Added `--limit` and `--start-after-id` options to `scripts/explanations/generate_explanations.py`.
- Changed explanation generation to process anomalies one at a time with progress output and independent transactions.
- Fixed a frontend pluralization typo where "anomalies" could render as "anomalyies".

## Problems Encountered

- Full news-context refreshes can be slow because live GDELT calls are rate limited and may retry with backoff.
- When interrupted with Ctrl+C, Python surfaces the exact wait point, which can look like a crash even when the underlying problem is an external provider delay or rate limit.
- A full explanation refresh may also be slow when the configured explanation provider calls an external model.

## Solution

The refresh scripts now support smaller, resumable runs. Local-only news context generation can use the internal macro timeline provider to avoid GDELT entirely during development. Progress output makes it clear which anomaly is currently being processed and how many rows were stored.

## Next Steps

- Prefer local-only bounded refreshes during UI development.
- Use live GDELT refreshes in small batches and expect provider-imposed delays.
- Consider adding explicit rate-limit warnings in the CLI output if GDELT returns HTTP 429.
